# msnw スピードテスト報告(2026 年 10 月)

msnw のトンネルを通したときに、素の回線の何パーセントの速度が出るかを、
ループバック・同一 LAN・インターネット越しの 3 つの環境で測った。
対象は msnw v0.1.13-4-g02623d9(go1.26.0)。途中で見つけた中継経路の性能問題を
修正し、修正後の値も載せている。

## 要約

| 環境 | 方向 | 素の回線 | 直結(ホールパンチ) | 中継(relay)経由 |
|---|---|---|---|---|
| 同一 LAN(1 GbE) | TCP 上り | 943 Mbit/s | 939 Mbit/s(**99.6%**) | 測定せず(LAN 内は直結になる) |
| 同一 LAN(1 GbE) | TCP 下り | 943 Mbit/s | 937 Mbit/s(**99.4%**) | - |
| 同一 LAN(1 GbE) | TCP 4 本合計 | 945 Mbit/s | 952 Mbit/s(**101%**) | - |
| 同一 LAN(1 GbE) | UDP 900 Mbit/s 時の損失 | 0% | 0.37% | - |
| インターネット | TCP 下り(回線 約 100 Mbit/s) | 95〜107 Mbit/s | 97〜145 Mbit/s(**100% 以上**) | 修正前 17〜20(**約 18%**)→ 修正後 90〜147(**95〜100% 以上**) |
| インターネット | TCP 上り(回線 約 870 Mbit/s) | 873 Mbit/s | 248〜300 Mbit/s(**28〜34%**) | 137〜149 Mbit/s(**16〜17%**) |
| ループバック(1 台) | TCP 上り | 71 Gbit/s | 2.0 Gbit/s | 1.2〜1.5 Gbit/s |

- **LAN では素の回線とほぼ同じ速度が出る**(99% 以上)。トンネルの負荷は
  見えない。
- **インターネット越しの下りは、直結なら素の回線と同等以上**、修正後の中継経由も
  素の 95〜100% 以上。修正前の中継経由は約 18% しか出ず、これが今回見つけた問題。
- **インターネット越しの上りは素の 3 割前後に留まる。** 今回の回線は上りで
  パケットを落とす(10 秒に約 200 回の TCP 再送)ため、QUIC の輻輳制御(cubic)
  がカーネルの TCP より強く引く。経路の損失に対する QUIC の弱さで、
  トンネルの処理負荷ではない(CPU は 115% 以下)。損失のない上りでは LAN と
  同様に回線速度に近づくはず。
- **ループバックの数値はトンネルの CPU 上限**で、回線との比率に意味はない。
  1 台で全プロセスを動かして直結 2.0 Gbit/s、中継 1.2〜1.5 Gbit/s まで出る。
  数百 Mbit/s の回線には十分な余裕がある。
- 接続の遅延: LAN で接続 + 最初の往復が素 1.31 ms → トンネル 3.36 ms(+2 ms)。
  インターネット越しでは素 29 ms、直結 19.6 ms、中継 19.3 ms で、トンネルの
  追加分は見えない(ローカルの TCP 接続が即座に完了し、QUIC 上の往復 1 回で
  相手に届くため)。

## 測定方法

- iperf3 で測る。msnw 経由の値は、importer がローカルに開けたポートに iperf3
  クライアントをつないだもの。「素の回線」は同じ 2 台の間で iperf3 を直接つないだもの。
- 1 回 10 秒(インターネット越しの素の回線は 8 秒)。表に 2 つ以上の値が並ぶのは
  別の回。「下り」は exporter 側から importer 側への転送(iperf3 `-R`)。
- UDP は固定レートで送って損失率と順序入れ替わりを見る。msnw で UDP を測るには
  同じポートの TCP(iperf3 の制御接続)も転送しておく必要がある。
- 「直結」はホールパンチで両端が直接 QUIC を張った状態、「中継」は
  `MSNW_FORCE_RELAY=1` で rendezvous サーバーの UDP リレーを経由させた状態。

### 環境

| 環境 | 構成 |
|---|---|
| 1. ループバック | server・export・import を 1 台(Linux、16 コア)で動かす |
| 2. 同一 LAN | 同じ 1 GbE スイッチ下の Linux 2 台。ホールパンチで直結になる |
| 3. インターネット | 自宅(下り約 100 Mbit/s、上り約 870 Mbit/s、IPv4 はトンネル型で経路 MTU 1460、IPv6 もあり)と、RTT 8.5 ms のデータセンター内の Linux ホスト。中継サーバーはそのデータセンター内の Linux(中継 A)と FreeBSD 14.5 の VM(中継 B)、および RTT 95 ms のクラウド(中継 C) |

## 環境 1: ループバック

|---|---|---|---|---|---|---|
| 素(lo) | 71 Gbit/s | 198 Gbit/s | - | - | - | - |

## 環境 3: インターネット越し

### 修正前

| 経路 | TCP 上り ×1 | TCP 上り ×4 合計 | TCP 下り | UDP 100M 損失 | UDP 200M |
|---|---|---|---|---|---|
| 素 | 873 | - | 107 / 98 | 0% | 損失 0% |
| 直結 | 248 / 300(28〜34%) | 206 | 145 / 131(100% 以上) | 0% | 167 受信 |
| 中継 A | 149 / 137(16〜17%) | 128 | **20 / 17(約 18%)** | 0% | - |

Mbit/s。中継を個別に強制した下り / 上り: 中継 A 16.4 / 69.7、中継 B 18.7 / 129、
中継 C 26.7 / 2.2。

直結の下りが素の TCP を上回るのは、素の iperf3(TCP 1 本、IPv4)が経路の
パケット損失で頭を抑えられているのに対し、QUIC は損失をストリーム単位で
回復するうえ、時間帯によっては IPv6 で繋がってより空いた経路を通るため。
「100% 以上」は回線側が上限という意味で読む。

中継経由の下りだけが約 18% と明らかに異常だった。

### 原因

中継サーバーが DF(Don't Fragment)ビットなしで UDP を送っていた。

1. 中継ホストのカーネルが、測定側の外部 IPv4 アドレス宛てに ICMP で学習した
   経路 MTU 1460 を経路キャッシュに持っていた(トンネル型 IPv4 回線の特徴)。
   中継ソケットは Linux 既定の `IP_PMTUDISC_WANT` なので、1468 バイトの QUIC
   パケットを 2 つに分割して送る。8 秒の中継下りで `IpFragOKs` が +8521、直結では 0。
2. 測定側ホストの再構成カウンター(`IpReasmReqds`)は 0。再構成しているのは
   手前の家庭用ルーターで、それが順序を入れ替えて出す。受信側 qlog で IPv4 中継の
   1-RTT パケットの 29.7〜40% が順序外(数個ずつ逆順、ずれ 13 以内)。
   **同じ中継プロセスに IPv6 で繋ぐと順序外 0、114 Mbit/s。**
3. 送信側 qlog では中継接続の損失判定 1117 のうち 1102 が後から ACK された誤判定
   (spurious loss)、回復処理 472 回。直結は損失 215、誤判定ほぼ 0。QUIC が順序の
   入れ替わりを損失と取り、輻輳ウィンドウを削り続けていた。
4. FreeBSD の中継 B は自分では分割しない(ip フラグメント統計 0)が、DF なしの
   1464 バイトのパケットを ISP のトンネル入口が分割していると見られ、同じ症状(7% が順序外、
   約 30 Mbit/s)。直結は quic-go が DF 付きで送るので影響を受けない。

否定した仮説: 中継ソケットの溢れ(drop カウンター 0、バッファを 8 MB にしても
変わらず)、中継のポート(8 ポート全部遅い)、送信元アドレス、ECN、GSO、
中継ホスト側の順序入れ替わり(同じ DC 内の受信側では 0)、経路の追加損失
(固定レート UDP で中継 0.59%、直結 0.86%)。natsim(ネットワーク名前空間での
NAT 模擬)では再現しない。

### 修正(internal/rendezvous)

- 中継ソケットに DF を設定(Linux `IP_PMTUDISC_PROBE`、macOS/FreeBSD `IP_DONTFRAG`、
  Windows `IP_DONTFRAGMENT`)。経路 MTU を超えたパケットは `EMSGSIZE` で捨てて数え
  (`relay: refused N packets larger than the path MTU`)、QUIC の MTU 探索に任せる。
  実際に 1432 バイトに落ち着く。
- FreeBSD/macOS はデュアルスタック(AF_INET6)ソケットでは IPv4 送信に DF を
  付けられないので、IPv4 のリッスンアドレス(0.0.0.0 を含む)では `udp4` ソケットを開く。
  運用では `-listen 0.0.0.0:4433 -relay 0.0.0.0:4434` と明示する。tcpdump で
  束縛前 `flags [none]`、束縛後 `flags [DF]` を確認。
- 読み取りと書き込みを別 goroutine に分離(キュー 4096)、Linux は `recvmmsg` で
  まとめ読み。ソケットバッファは 8 MB を要求し、失敗したら半分ずつ下げる
  (FreeBSD は `kern.ipc.maxsockbuf` 既定 2 MB で 8 MB 要求が ENOBUFS になり、
  Go は丸めてくれないため、従来は既定の 42 KB のままだった)。
- README に DF の説明と FreeBSD での起動引数、sysctl の設定例を追記。
  `QLOGDIR` で quic-go の qlog を書けるようにした(デバッグ用)。

## その他の観測

- 正常な TCP クローズのたびに importer が猶予期間いっぱい RESUME を再試行する
  (0.5 秒から 5 秒まで倍々)。`-v` で「resume xxx: no such session」のあと
  「could not be resumed」。データには影響しないが無駄なストリームが開く。
- ループバックの「直結」は 127.0.0.1 ではなく Tailscale のアドレスを選んだ。
- 1 本の QUIC 接続に TCP ×4 を通すと、どの環境でも ×1 より少し遅い。
- 測定に使った自宅回線の IPv4 下りは夜間に 16〜76 Mbit/s まで落ち、
  05:00 以降に 100 前後に戻る。測定は回線が静かな時間帯の値で比較すること。

## 再現手順

対向ホスト(exporter 側、iperf3 サーバーも同居):

```sh
iperf3 -s -p 15201 &
MSNW_KEY=1234 msnw export -n bench -t 15201 -u 15201
```

測定側(importer 側)。UDP の測定には同じポートの TCP 制御接続も必要なので
両方を転送する:

```sh
MSNW_KEY=1234 msnw import -v 16301=bench:15201 16301=bench:15201/udp &
iperf3 -c 127.0.0.1 -p 16301 -t 10          # 上り
iperf3 -c 127.0.0.1 -p 16301 -t 10 -R       # 下り
iperf3 -c 127.0.0.1 -p 16301 -t 10 -u -b 100M --json | grep -E 'lost_percent|out_of_order'
```

中継経路を強制するには `MSNW_FORCE_RELAY=1`、特定の中継を選ぶには
`-s HOST:PORT`(IPv4 リテラルなら中継も IPv4、`[v6]:PORT` なら IPv6)。
qlog を取るには exporter / importer に `QLOGDIR=/path` を与える。

中継ホスト側で分割が起きているかは次で分かる:

```sh
# Linux
ip route get CLIENT_IP            # "mtu 1460" のような経路キャッシュ
nstat -az IpFragOKs IpFragCreates # 中継下り中に増えれば分割している
# FreeBSD
netstat -s -p ip | grep -i fragment
tcpdump -ni IFACE -c 20 'udp and src port 4434'   # "flags [DF]" が付いているか
```
